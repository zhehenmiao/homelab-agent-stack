# 踩过的坑

**这是整个仓库里最有价值的一篇。** 每个坑都是真实故障，不是假设。

格式统一：**现象 → 根因 → 修法 → 教训**。

---

## 1. 私有网络把云厂商的内部服务全掐断了

**现象**

接入 Tailscale 后，云厂商的元数据接口、内网镜像源、监控上报、备份服务全部超时。表面上「网络好好的」（公网能通），但机器像被切断了半条命。

**根因**

Tailscale 安装时往 iptables 塞了一条规则：

```
-s 100.64.0.0/10 ! -i tailscale0 -j DROP
```

意思是「任何来自 100.64.0.0/10 的包，只要不是从 tailscale0 进来的，一律丢弃」。

**但云厂商的内部服务用的正是 `100.100.0.0/16` 网段** —— 它落在这个 C 段里，于是被一并丢弃。

**修法**

在 DROP 规则之前插入放行规则，按接口而非网段判断：

```bash
# 放行从主网卡进来的同网段流量
iptables -I INPUT -s 100.64.0.0/10 -i eth0 -j ACCEPT
```

并固化成开机脚本 + systemd drop-in，避免重启后失效。

**教训**

**第三方工具的安全默认值，可能和云环境的内部约定冲突。** 组网成功不代表服务正常 —— 部署网络层之后，必须把依赖内部服务的功能全测一遍，而不是只测能不能 ping 通。

## 2. 服务不能重启自己

**现象**

给网关服务加了个「一键重启」的 API。调用后返回成功，但服务没重启，或者重启到一半彻底失联。

**根因**

进程调用 `systemctl restart <自己>` 时，systemd 会先杀掉这个进程（连同它发起的重启命令），于是命令执行到一半就断了。用 `systemd-run` 也一样 —— 父进程一死，子进程跟着被清理。

**修法**

把重启动作**投递出去**，交给系统外部的执行者：

```bash
# 用一个一次性定时任务在 1 分钟后执行重启
echo "$(date -d '+1 min' '+%M %H') systemctl restart myservice" | crontab -
```

进程立刻返回，真正的重启由 cron 在下一分钟执行。

**教训**

**任何「让进程终止自己」的操作，都要由外部执行器完成。** 这是自我托管系统的通用模式，不止 systemd —— 容器里自杀、消息队列里自删消费者，都是同一个问题。

## 3. 多实例路由：消息全落到了错误的地方

**现象**

两个 Agent 实例跑在同一台机器的不同端口上。A 给 B 发消息，对方收到了，但**没有回应**，日志里也没有报错。

**根因**

服务同时托管多个 profile，路由按 URL 前缀区分：

```
/               → 默认 profile
/p/alice/       → A 实例
/p/bob/         → B 实例
```

发消息时用了根路径，于是消息全部进了默认 profile —— 一个没配置人设、没人看的实例。**消息「成功送达」了，只是送错了人。**

**修法**

所有跨实例调用必须带完整前缀，并在文档里写死。

**教训**

**「请求成功」和「业务生效」是两件事。** 多租户系统里，默认路由是最危险的路径 —— 它永远不报错，只是默默地做错事。发消息前先验证「对面是谁」。

## 4. 一个数据源挂了，整份报告全废

**现象**

每天早上生成的报告，某天只发出一句「抓取失败」。检查发现三个数据源里只有一个超时，另外两个完全正常 —— 但用户什么都没拿到。

**根因**

脚本没有分源容错。三个源的请求写在一个 try 块里，第一个抛异常，整个 `main()` 直接退出。**而且失败发生在生成阶段，用户连「部分成功」的结果都看不到。**

**修法**

```
每个源独立 try/except
可重试错误（429 / 5xx / 超时）：读 Retry-After 退避重试，最多 3 次
主源失败：自动切换备用源（RSS → API → 页面解析）
全部失败：输出一份「降级报告」，明确标注哪部分缺了
```

**教训**

**聚合类任务的失败粒度，必须和用户感知的粒度对齐。** 三个源挂一个，用户该拿到三分之二的内容加一行提示，而不是一句「失败」。

## 5. 一条空字段，堵住了整条通道

**现象**

消息能发出去，但收不到。检查数据库发现有会话记录，字段也在，就是没内容进来。

**根因**

某次自动化创建了一个会话对象，但它的路由键（`chat_id`）是空字符串。后续所有投递都匹配到这个空壳会话，写进了一个没人读的地方。

**修法**

清理空壳记录 + 投递前校验路由键非空。

**教训**

**自动化创建的实体，必须有完整性约束。** 人手动创建时会自然填全字段，脚本不会 —— 凡是脚本能创建的记录，都要有非空校验。

## 6. 内存「泄漏」其实是误判

**现象**

内存占用一直在 70% 以上，怀疑泄漏，准备重启服务。

**根因**

Linux 的 `used` 包含可回收的 page cache。真正的可用内存要看 `available` 字段，不是 `1 - used%`。

**修法**

按可用量判断，并且看趋势而不是瞬时值：

```bash
free -m | awk 'NR==2{print "可用 "$7" MB"}'
```

再配合定时采集的 RSS 历史，判断「有没有贴着峰值不回落」。

**教训**

**别用二手指标做决策。** 「内存占用 70%」在不同的口径下可能是完全健康的系统。判断泄漏要看**进程 RSS 是否单调上升且夜间不回落**，而不是看一个百分比。

## 7. 换了个更"强"的模型，输出反而全空

**现象**

报告生成模块换成新一代推理模型后，返回的正文全是空的。API 没报错，token 账单正常扣费。

**根因**

推理模型会先产出「思考过程」，再产出「正文」。当 `max_tokens` 设置较小时，预算全被思考过程吃掉，正文部分一个字都没剩下。

**修法**

生成类任务改用非推理模型；或者在代码里检测空内容并抛错，而不是静默返回空字符串。

**教训**

**「更强的模型」不是无条件的替换。** 推理模型适合需要思考的任务，不适合结构化生成。切换任何模型前，先看它的输出协议，不只看 benchmark。

## 共性总结

翻完这七个坑，会发现它们全在同一个模式上：

```
「成功」返回了   ≠   事情做对了
```

- 组网成功 ≠ 服务正常（坑 1）
- 重启命令返回成功 ≠ 服务重启了（坑 2）
- 消息发送成功 ≠ 送到了对的人（坑 3）
- 请求成功 ≠ 数据完整（坑 4）
- 记录存在 ≠ 内容有效（坑 5）
- 指标数值 ≠ 系统健康（坑 6）
- API 调用成功 ≠ 输出有内容（坑 7）

**所以运维的核心不是「让命令成功」，而是「验证结果正确」。** 所有自动化流程都要有端到端验证，不能停在「调用返回 200」。
