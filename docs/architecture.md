# 架构与设计权衡

## 一、节点角色划分

```
中枢节点（云服务器，2C2G）
  职责：消息通道、任务调度、监控汇总、知识检索
  不干：任何持续消耗 CPU/内存的业务
  理由：常驻成本最低，且公网可达（自愈、远程接入都靠它）

边缘节点（若干台，配置各异）
  职责：实际业务负载、数据采集
  不干：对外暴露服务
  理由：分散负载，一台挂了不影响全局

本地节点（开发机）
  职责：开发、备份、物理操作
  不干：承担必须 7×24 在线的职责（会关机）
  理由：把「可能离线」的设备排除在关键路径外
```

**关键判断：中枢只做容易恢复的事。** 调度器和通道本身是无状态的，挂了重启即可；任何有状态的重活都放在边缘。

## 二、为什么不用容器编排

| 方案 | 适合场景 | 本项目为什么不用 |
|---|---|---|
| Kubernetes | 多节点弹性伸缩、服务网格 | 单机编排的控制面就要 1~2 GB 内存，比整个中枢的预算还高 |
| Docker Compose | 单机多容器 | 在部分节点上用了；但不是所有负载都需要隔离 |
| 裸机 + systemd | 少量长驻服务 | **主选**：零额外开销，日志和自愈都是原生的 |
| 纯 cron | 定时任务 | **主选**：内存占用接近零，能挂几十个任务 |

**结论**：编排系统解决的问题是「规模」，这里的规模是 5 台机器、十几个任务 —— 引入编排是负收益。

## 三、网络设计

```
公网
 └─ 只有一个 SSH 端口（限 IP 白名单）
     └─ 私有网络（WireGuard / Tailscale）
         ├─ 服务端口全部只绑内网地址
         └─ 节点之间互相直连
```

**为什么服务只绑内网**

1. 公网端口一开就是攻击面，安全组配置错一次就裸奔
2. 内网通信不需要证书和域名，省掉一堆配置
3. 端口不暴露，扫描器看不到，日志噪音也少

**代价**：私有网络层故障时，所有服务同时不可达。
**缓解**：把网络层当成关键依赖对待 —— 改动网络配置必须有回滚方案，且要验证云厂商内部服务仍可用（见 `pitfalls.md` 坑 1）。

## 四、自愈的三层设计

```
第一层  systemd Restart=always
        解决：进程崩溃、OOM 被杀
        延迟：秒级
        盲区：进程活着但卡死（无响应）

第二层  守护脚本（每 5 分钟）
        检测：健康检查接口 + 内存水位
        动作：连续失败则强制重启
        盲区：主机整体失联

第三层  巡检任务（每 15 分钟）
        检测：端到端业务可用性（发消息能否收到回复）
        动作：告警 + 尝试恢复
        盲区：需要人判断的复杂故障
```

**为什么不合并成一层**

三层解决的是**不同层级的故障**：进程层、服务层、业务层。合并会导致要么救不了卡死，要么发现太慢。

**为什么周期是 5 分钟和 15 分钟**

- 太频：日志刷屏、告警疲劳
- 太缓：故障持续太久
- 这两个值是基于「用户容忍断线多久」倒推的，不是拍脑袋

## 五、监控与可观测性

```
采集
  · 每小时记录内存 RSS、公网流量、磁盘
  · 所有记录写 CSV（不用数据库：数据量小，CSV 能直接读、能 diff、能进 git）

展示
  · 单页看板，只走内网
  · 数字必须和命令行一致（不接受近似值）

判断
  · 看趋势不看瞬时
  · 看可用量不看百分比
  · 看是否贴着峰值不回落（泄漏特征）
```

**为什么不用 Prometheus + Grafana**

那套组合的常驻开销在中枢节点上占 30% 以上的内存预算，而这里要监控的对象只有 5 台机器。**用 200 行脚本能解决的事，不引入一整套生态。**

## 六、成本账

```
中枢节点      共享型 2 核 2G，包年
流量          20 GB/月，实测公网出约 4.4 GB/月（大头是模型 API 请求）
边缘节点      按需，多数是已有的机器
存储          40 GB 系统盘，实际用 13 GB
```

**关键设计**：把「可能花钱的地方」都量化记录，异常能被发现。比如公网流量为什么是模型 API 上行而不是下载 —— 这类反直觉的数字必须查清楚，否则估算会错一个量级。

## 七、这套架构的边界

**扛得住**

- 单节点故障（其他节点不受影响）
- 单服务崩溃（三层自愈）
- 单数据源故障（降级继续）
- 一个人维护（所有操作有文档）

**扛不住**

- 中枢节点整机故障 → 全盘停摆（没有做多活）
- 私有网络层故障 → 节点间失联
- 流量突增 → 没有弹性伸缩
- 并发用户规模上去 → 单机架构不适用

**这些不修的判断依据**：当前是单人使用场景，可用性要求是「小时级恢复」，不是「秒级永不中断」。**为不存在的需求做冗余，是把复杂度换成心理安慰。**

## 八、如果重来会怎么改

```
① 中枢的关键状态外置
   现在调度器和通道的状态存在本地，迁移要停机
   重来会把状态放到独立的轻量存储里

② 网络层改动加自动化验证
   坑 1 那种故障，如果部署后自动跑一遍「内部服务连通性检查」，能当场发现

③ 告警分级
   现在所有告警一个通道，重启这类自愈动作也会通知
   应该区分「已自愈」和「需要人管」
```
