# 日常运维手册

## 每天

```bash
# 一眼看健康度
uptime                          # 负载
free -m | awk 'NR==2{print "可用 "$7"/"$2" MB"}'
df -h / | awk 'NR==2{print "磁盘 "$3"/"$2}'
systemctl --failed              # 有没有失败的服务
```

**判断标准**

```
负载        持续高于核数 × 1.5  → 查
可用内存    跌破 400 MB         → 查
磁盘        超过 80%            → 清
失败服务    有一个就该看
```

## 每周

```
□ 检查定时任务有没有静默失败（看日志，不是看有没有跑）
□ 检查磁盘增长趋势
□ 看一遍异常日志（不只看 error，也看 warn 的频率）
□ 确认备份完成了（不能只看任务返回成功，要抽查文件）
```

## 常见故障处理

### 服务无响应但进程还在

```bash
# 1. 确认是不是真无响应
curl -s -m 5 http://<内网地址>:<端口>/health || echo "无响应"

# 2. 看进程状态
systemctl status <服务名>

# 3. 看是不是内存问题
grep VmRSS /proc/$(systemctl show -p MainPID --value <服务名>)/status

# 4. 重启（如果服务本身不支持自我重启，用外部触发，见 pitfalls 坑 2）
systemctl restart <服务名>
```

### 内存告警

```bash
# 先分清是「真占用」还是「cache」
free -m

# 看是哪个进程吃的
ps -eo pid,rss,comm --sort=-rss | head -10

# 看历史趋势（有没有贴着峰值不回落）
tail -20 <内存历史日志>
```

**别急着重启**：先判断是不是泄漏。判断依据见 `pitfalls.md` 坑 6。

### 定时任务没产出

```bash
# 1. 任务跑了吗（看调度器日志，不是看结果文件）
grep <任务名> <调度日志>

# 2. 跑了但失败了
看任务自己的输出日志，重点找外部依赖的错误（network、rate limit、auth）

# 3. 跑了也成功了，但没收到通知
查通道——这是最容易忽略的一层（见 pitfalls 坑 3）
```

### 网络层异常

```bash
# 1. 私有网络状态
tailscale status

# 2. 节点互通
ping -c 3 <对端内网 IP>

# 3. 云厂商内部服务（最容易被网络改动掐断）
curl -s -m 3 http://100.100.100.200/latest/meta-data/instance-id && echo "元数据正常"
curl -s -m 5 -o /dev/null -w '%{http_code}\n' https://mirrors.aliyun.com/  # 内网镜像
```

**第 3 条特别重要**：改动网络配置后，公网通不代表内部服务通。这是坑 1 的直接教训。

## 部署新服务

```
① 先算内存预算 —— 可用内存不到 400 MB 就别上
② 写成 systemd 单元，加 Restart=always
③ 服务只绑内网地址，不开公网
④ 加健康检查接口
⑤ 加进巡检（不然挂了没人知道）
⑥ 更新文档 —— 不然三个月后自己都不记得
```

## 备份

```
频率    每周
方式    拉到本地（不放在云上，云盘坏了本地还有）
验证    抽查文件能不能打开，不只看任务返回成功
```

**备份最危险的不是没跑，是跑了但文件是坏的。** 每月抽查一次恢复。

## 应急：中枢节点整机故障

```
1. 重新开一台同配置机器
2. 装基础环境（脚本见 scripts/）
3. 恢复配置和状态
4. 把私有网络节点重新加入
5. 验证：发一条消息能收到回复
```

**预计恢复时间**：30~60 分钟。**没有做多活，这是已知的单点。**

## 变更前必做的三件事

```
① 备份当前状态（配置文件复制一份，带日期）
② 想清楚回滚怎么做
③ 挑影响最小的时间窗口
```

**别在没有回滚方案的深夜里改生产配置。**
